Ваши серверы сами звонят домой. Агент получает структурный shell на любой машине, даже за NAT — ключи, периметр и kill switch остаются у вас.

![mcp-node-zig: холодный старт, вызов exec и список живых сессий на локальном узле (v0.5.0)](assets/demo.gif)

mcp-node-zig — один статический бинарь, который говорит на MCP. Положите его на машину, и агент сможет запускать там команды, вести долгие сессии, читать и писать файлы. Нода сама звонит на ваш хаб (это тот же бинарь), поэтому машина не открывает входящих портов, SSH-ключ к агенту не попадает, а чужого облака на пути нет. Канал взаимно аутентифицирован HMAC-SHA256 и идёт через TLS, хаб ограничивает рукопожатия по источнику, а каждый вызов инструмента может лечь в аудит-лог с защитой от подделки.

**2.0 мс** холодный старт · **1.2 мс** p50 вызова exec · **1.57 МиБ** RSS в простое · **9.6 МиБ** бинарь ([бенчмарки](BENCHMARKS.md))

## Установка

```sh
curl -fsSL https://raw.githubusercontent.com/alexchen-sys/mcp-node-zig/main/install.sh | sh
```

Скрипт сам определяет платформу, скачивает свежий релиз, сверяет его с `SHA256SUMS.txt` и ставит в `/usr/local/bin` (или `~/.local/bin`). Хаб со встроенным TLS-сервером: `MCP_NODE_FLAVOR=tls` (релизы Linux и macOS). Зафиксировать версию: `MCP_NODE_VERSION=0.5.0`, другой каталог: `PREFIX=/some/dir`.

Ручная установка, Linux x86_64:

```sh
curl -L https://github.com/alexchen-sys/mcp-node-zig/releases/download/v0.5.0/mcp-node-v0.5.0-x86_64-linux.tar.gz | tar xz
```

Другие цели на [странице релизов](https://github.com/alexchen-sys/mcp-node-zig/releases): `aarch64-linux`, `aarch64-macos`, `x86_64-windows`. В каждом релизе есть `SHA256SUMS.txt`, подписанный [cosign](https://github.com/sigstore/cosign) без ключей (Sigstore); `install.sh` проверяет подпись, если cosign есть в PATH.

## Быстрый старт

```sh
openssl rand -hex 32 > token
./mcp-node-v0.5.0-x86_64-linux/mcp-node &

curl -sS http://127.0.0.1:8341/mcp \
  -H 'Content-Type: application/json' \
  -H "X-Node-Token: $(cat token)" \
  --data '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"sys_info","arguments":{}}}'
```

В ответ придут имя хоста, ОС, load, память и uptime в виде JSON. Теперь подключите агента:

```sh
claude mcp add --transport http mcp-node http://127.0.0.1:8341/mcp \
  --header "X-Node-Token: $(cat token)"
```

## Зачем это

- **Ключи остаются у вас.** Агент держит токен ноды, а не SSH-ключ. Остановите ноду — доступа нет; смените токен — все старые копии перестают работать.
- **Ничего не нужно готовить.** Ни Node, ни Python, ни OpenSSH, ни ключей для раздачи. Скопируйте один файл и запустите.
- **Процессы живут дольше запросов.** Запустите сборку, отключитесь, вернитесь и прочитайте вывод по смещению.
- **Дёшево держать включённым.** 1.57 МиБ в простое. Каждый дополнительный подключённый агент добавляет около 304 КиБ, а не второй процесс сервера на ~100–150 МиБ.
- **Без shell, пока вы не попросите.** `exec` передаёт argv как есть. `exec_shell` — единственный явный слой shell.
- **Убивает всё дерево.** Группы процессов на POSIX, Job Objects на Windows. Никаких осиротевших детей, держащих пайпы.
- **Каждый вызов остаётся в журнале.** Включите аудит-лог, и каждый вызов инструмента оставит HMAC-сцепленную строку JSONL, которую `audit-verify` проверяет офлайн.
- **Linux, macOS, Windows.** Все три собираются и проходят smoke-тесты в CI на каждый пуш.

## Чем это отличается от SSH?

Это разные задачи, и вместе они работают хорошо.

SSH — защищённый транспорт и терминал для человека. В нём есть шифрование, управление ключами, agent forwarding, PTY, scp/sftp/rsync и десятилетия харденинга. Всё это продолжайте использовать.

mcp-node — это API исполнения для агентов. Через SSH агент получает одну строку, которую удалённый shell разберёт заново, плюс сырые байты и код выхода. Здесь он получает:

- **argv без shell.** Никакого второго круга квотирования для удалённого shell. Shell используется только тогда, когда вы просите `exec_shell`.
- **Структурированные результаты.** `stdout`, `stderr`, `exit_code`, `truncated_*` и тайминги как JSON, с таймаутами на каждый вызов.
- **Сессии, которые живут дольше запроса.** `exec_start`, затем `exec_poll` по байтовому смещению, `exec_write` в stdin, `exec_wait` до 300 с, `exec_kill` для всего дерева. Оборванное соединение не убивает сборку.
- **Проверенная запись файлов.** `write_file` принимает plain text или base64 и возвращает SHA-256 того, что легло на диск.
- **Самоописывающийся интерфейс.** Любой MCP-клиент узнаёт инструменты из `tools/list`; агенту не нужно ничего объяснять.

Для удалённых машин [обратное подключение](#обратное-подключение-без-входящих-портов) заменяет туннель: на целевой машине не нужен sshd, а ключ не попадает к агенту. Где SSH уже стоит, они работают в паре: нода слушает `127.0.0.1`, а порт пробрасывается (`ssh -L 8341:127.0.0.1:8341 host`).

## Обратное подключение (без входящих портов)

Машину за NAT или без sshd запускают с `--connect hub:port`: нода сама звонит хабу (тот же бинарь с `MCP_NODE_HUB_LISTEN`), а клиенты ходят к ней через `/n/<name>/mcp` на хабе. По умолчанию канал идёт через TLS: порт хаба для нод слушает `127.0.0.1`, перед ним стоит TLS-терминатор (nginx `stream`, stunnel, HAProxy), а нода подключается с `MCP_NODE_CONNECT_TLS=1`:

```sh
# хаб; nginx/stunnel принимает TLS на :8400 и передаёт на 127.0.0.1:8401
MCP_NODE_HUB_LISTEN=127.0.0.1:8401 MCP_NODE_HUB_SECRET_FILE=nodes ./mcp-node
# нода; в `nodes` на хабе строка laptop:<secret>, в `secret` здесь только <secret>
MCP_NODE_NAME=laptop MCP_NODE_CONNECT_SECRET_FILE=secret MCP_NODE_CONNECT_TLS=1 \
  ./mcp-node --connect hub.example.com:8400
```

Релизная сборка `-tls` (или любой бинарь, собранный с `-Dtls-server`) умеет сам служить TLS на порту для нод (`MCP_NODE_HUB_TLS_CERT_FILE` / `MCP_NODE_HUB_TLS_KEY_FILE`), без терминатора спереди; тогда хаб видит настоящие адреса пиров и его лимиты рукопожатий по источнику работают в полную силу.

Полная настройка, конфиг терминатора и вариант с голым TCP для доверенных сетей — в [docs/reverse-connect.md](docs/reverse-connect.md).

## Режим stdio

Клиенты, которые сами запускают сервер подпроцессом, могут звать ноду напрямую с флагом `--stdio` (или `MCP_NODE_STDIO=1`). Сообщения идут построчно в формате JSON-RPC: один запрос на строку в stdin, один ответ на строку в stdout. Порт не слушается и токен не нужен: пайпы держит тот, кто запустил процесс. Логи пишутся только в stderr; когда stdin закрывается, нода выходит с кодом 0 и убивает все ещё работающие недолговечные сессии (долговечные — ровно то самое исключение по желанию: они отцепляются и выживают, см. [Долгоживущие сессии](#долгоживущие-сессии)).

```json
{
  "mcpServers": {
    "mcp-node": {
      "command": "mcp-node",
      "args": ["--stdio"]
    }
  }
}
```

`--stdio` нельзя совмещать с `--connect` и `MCP_NODE_HUB_LISTEN`.

## Аудит-лог

Задайте `MCP_NODE_AUDIT_FILE` — и каждый вызов инструмента оставляет одну
append-only JSONL-запись, сцепленную HMAC-SHA256: правки, удаления и
перестановки прошлых записей обнаруживаются офлайн:

```sh
openssl rand -hex 32 > audit-key && chmod 600 audit-key
MCP_NODE_AUDIT_FILE=/var/log/mcp-node.jsonl MCP_NODE_AUDIT_KEY_FILE=./audit-key ./mcp-node
mcp-node audit-verify --anchor /var/log/mcp-node.jsonl
```

Нода пишет каждый `tools/call` (инструмент, транспорт, пир, сводку аргументов
по инструменту, результат), хаб пишет маршрутизацию `relay` и события линков;
обе стороны сходятся по `req_id`. Скрипты, содержимое файлов и stdout не
пишутся никогда. Подробности и модель угроз: [docs/audit-log.md](docs/audit-log.md).

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `sys_info` | имя хоста, ОС, load, память, uptime |
| `exec` | выполнить argv до завершения, без shell; `max_bytes`/`head_lines`/`tail_lines` подрезают длинный вывод |
| `exec_shell` | выполнить скрипт через `bash`/`sh`/`fish`/`zsh`, на Windows — `cmd`/`powershell`; та же подрезка вывода, что у `exec` |
| `exec_start` | запустить долгоиграющий процесс как сессию |
| `exec_poll` | читать вывод сессии с байтовых смещений, `max_bytes` задаёт страницу |
| `exec_wait` | ждать выхода сессии или `timeout` (по умолчанию 30 с, максимум 300 с) |
| `exec_write` | записать base64-байты в stdin; `eof=true` закрывает его |
| `exec_kill` | убить дерево процессов сессии |
| `exec_close` | освободить сессию; идемпотентно |
| `exec_list` | перечислить живые сессии |
| `read_file` | читать UTF-8 текст с offset/limit или построчными окнами `line_offset`/`line_limit` |
| `write_file` | записать plain text (`content`) или base64 (`content_b64`), создать родительские каталоги, вернуть SHA-256 |
| `list_dir` | перечислить элементы с типом, размером, mtime |
| `copy_path` | скопировать файл или дерево каталогов в точный новый пункт назначения; со стейджингом и атомарной публикацией, никогда не перезаписывает |

Полные схемы — через `tools/list`. Таймауты `exec` и `exec_shell` по умолчанию 120 с, зажимаются в 1–1800 с.

## Долгоживущие сессии

Exec-сессии живут в процессе ноды, а не в соединении. Сессия переживает
разрыв линка хаб<->нода, рестарт хаба и любой обрыв клиента: захват вывода
продолжается, пока никто не опрашивает, а после реконнекта тот же
`session_id` продолжает с байтовых смещений вашего последнего ответа
(без дыр и дублей). `exec_list` восстанавливает id, если ответ потерялся.

По умолчанию сессии хранятся в памяти (после рестарта процесса ноды из-за сбоя,
OOM-kill или перезагрузки старый id возвращает `unknown_session`). Вывод на поток ограничен
`MCP_NODE_MAX_OUT` байтами; при достижении лимита голова сохраняется,
ставится флаг `truncated_*`, а счётчик `lost_*_bytes` показывает число
отброшенных байт. Завершённые сессии удаляются через `MCP_NODE_SESSION_TTL_S` после
окончания; активные сессии по таймеру не удаляются.

### Опциональная дисковая персистентность (`durable: true`)

С заданным `MCP_NODE_STATE_DIR` (или `--state-dir`) `exec_start` принимает
`"durable": true`: stdout/stderr дочернего процесса со старта дописываются в
файлы логов сессии на диске, а метаданные сессии фиксируются до начала
вывода. После рестарта нода восстанавливает сессию:
`exec_poll` по тому же id возвращает `recovered: true` с побайтовыми
дельтами от ваших смещений, а `exec_kill` проверяет идентичность процесса
(PID + время старта + id загрузки) перед отправкой сигнала. Лидер получает
сигнал через pidfd, поэтому сигнал не попадёт в переиспользованный PID.
Узкая гонка остаётся, если группа процессов завершилась и её числовой ID
был выдан новой группе между проверкой идентичности и отправкой сигнала группе.

Данные на диске: `argv`, `cwd` и полные логи stdout/stderr хранятся в каталоге
состояния **открытым текстом** (учитывайте это, если команды выводят секреты).
Каталог остаётся локальным на диске ноды и требует прав `0700`.

Ограничения восстановленной сессии отражаются в полях ответа:
`stdin_available: false` (`exec_write` возвращает `StdinUnavailable`), а если
дочерний процесс завершился во время простоя ноды, `exit_code` равен `null`
с `completion_reason: "orphaned_exit"`. Записи привязываются к хешу токена-владельца
(owner binding) при активном файле политик; без файла политик все запросы
используют общий нулевой идентификатор владельца.
Закрытая или удалённая по TTL durable-сессия возвращает `unknown_session` с
`expired: true` в пределах окна хранения томбстоунов. `durable: true` без
каталога состояния отклоняется как `DurabilityDisabled`; сам каталог обязан
иметь права `0700` и защищён flock-блокировкой от второго экземпляра ноды (`StateDirLocked`).
Общий объём каталога состояния ограничен `MCP_NODE_STATE_MAX_BYTES` (по
умолчанию 64 МиБ). В v0.5.0 durable-сессии поддерживаются на Linux; на других
платформах возвращается `DurabilityUnsupported`.

Неизвестный или истёкший `session_id` возвращает
`{"ok": false, "error": "unknown_session", "session_id": ..., "expired": ..., "message": ...}`
как структурированный ответ инструмента (`isError: true`) вместо ошибки протокола JSON-RPC `-32602`.
`expired: true` значит, что эта нода недавно держала сессию и закрыла,
собрала или вытеснила её (окно свежести ограничено: давно удалённые id
забываются и отвечают `expired: false`, как и id, которых тут никогда не
было или что старше рестарта ноды — сообщение об этом говорит). Для того
же случая `exec_close` сохраняет идемпотентный
`{"ok": true, "already_closed": true}`.

## Клиенты

У всех клиентов ниже один и тот же URL и токен. `Authorization: Bearer <token>` работает везде; `X-Node-Token: <token>` принимается для клиентов, которые не умеют задавать `Authorization`.

Cursor (`.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "mcp-node": {
      "url": "http://127.0.0.1:8341/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

VS Code (`.vscode/mcp.json`):

```json
{
  "servers": {
    "mcp-node": {
      "type": "http",
      "url": "http://127.0.0.1:8341/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

Codex (`~/.codex/config.toml`):

```toml
[mcp_servers.mcp-node]
url = "http://127.0.0.1:8341/mcp"
http_headers = { "Authorization" = "Bearer <token>" }
```

Claude Desktop и другие JSON-клиенты: как Cursor, плюс `"type": "http"`.

Клиенты, которые умеют только stdio: запустите саму ноду с `--stdio` (см. [режим stdio](#режим-stdio)) или поставьте мост к удалённой ноде по HTTP через `npx mcp-remote http://127.0.0.1:8341/mcp --header "Authorization: Bearer <token>"`.

## Безопасность

- **Токен обязателен.** С отсутствующим или пустым файлом токена сервер не стартует. Сравнение идёт за константное время.
- **Ограничение аргументов по токену (опционально).** `MCP_NODE_POLICY_FILE` задаёт, что может делать каждый клиентский токен на уровне аргументов: allowlist по argv[0], префиксы путей для чтения/записи/cwd, потолки таймаута и режима записи, сессии, принадлежащие токену. См. [права по аргументам](docs/arg-gating.md), пример конфига — в разделе [права токенов](#права-токенов).
- **По умолчанию только loopback.** Слушает `127.0.0.1`. Чтобы выставить наружу, задайте `MCP_NODE_HOST` и добавьте `host:port`, по которому ходят клиенты, в `MCP_NODE_ALLOWED_HOSTS`.
- **Host и Origin проверяются** до разбора тела: неизвестный Host получает 421, неизвестный Origin — 403.
- **TLS на канале.** Линк ноды идёт через TLS — его отдаёт сам хаб в сборке `-Dtls-server` или любой терминатор. Локальный HTTP API остаётся на loopback; чтобы выставить наружу, поставьте спереди reverse proxy, туннель или VPN, например `caddy reverse-proxy --from node.example.com --to 127.0.0.1:8341`.
- **Токен — это shell пользователя, от которого запущена нода.** Запускайте её под аккаунтом, ограниченным тем, чего агент должен касаться.

## Модель безопасности

- **Кто держит клиентский токен, тот запускает команды.** На обычной ноде это значит саму ноду; на хабе токен достаёт до каждой подключённой ноды, так что считайте токен хаба суммой всех.
- **Хаб видит всё.** TLS кончается на нём (или перед ним), поэтому он обрабатывает каждый запрос и ответ в открытом виде, а хаб, у которого есть секрет ноды, может запустить на ней что угодно.
- **Секрет ноды — это shell на ней и владение её именем.** В строках `name:secret` у каждого имени свой секрет; один общий секрет позволяет любому держателю подключиться под любым именем, в том числе ещё не занятым.
- **Рукопожатие аутентифицирует, и каждый следующий кадр помечается.** Хаб и нода доказывают знание секрета через HMAC-SHA256 по свежим nonce, а кадры после рукопожатия несут HMAC-SHA256-метки на каждое направление со строгими порядковыми номерами, так что активный релей не может их подделать, переставить или воспроизвести. Кадры по голому TCP по-прежнему не шифруются: релей может их прочитать (но не изменить).
- **TLS — на всём, что вы не контролируете.** `MCP_NODE_CONNECT_TLS=1` заставляет ноду проверять цепочку сертификатов и имя сервера, и выключателя для этого нет. Бинарь, собранный с `-Dtls-server`, сам отдаёт TLS на порту линка хаба (см. [обратное подключение](#обратное-подключение-без-входящих-портов)); иначе терминируйте TLS перед этим портом и держите порт на loopback.
- **Голый TCP — только для того же хоста или доверенной LAN.**
- **Лимиты рукопожатий считаются по адресу источника.** Хаб ведёт не больше 16 неаутентифицированных рукопожатий всего и 4 с одного IPv4-адреса или IPv6 /64, а 8 неудачных рукопожатий за минуту блокируют источник на минуту. Адреса 127.0.0.1 и ::1 из лимита исключены, поэтому за локальным TLS-терминатором все ноды выглядят одним адресом: задайте лимит на IP в самом терминаторе (nginx `limit_conn`) и, где можно, откройте публичный порт в файрволе только для известных адресов. Со встроенным TLS-сервером хаб видит настоящий адрес пира, и лимиты работают в полную силу.
- **Права включаются по желанию, это не песочница.** Без `MCP_NODE_POLICY_FILE` любой токен может вызвать любой инструмент; с ним каждый токен получает свой список инструментов и границы аргументов ([права по аргументам](docs/arg-gating.md)). Разрешённый интерпретатор — всё равно произвольный код.
- **Вне области:** песочница и скомпрометированный хост хаба или ноды. Нода работает с полными правами своего пользователя ОС. (Аудит-лог замечает подделку записей; он не защитит от того, кто контролирует хост.)

## Права токенов

`MCP_NODE_POLICY_FILE` превращает один общий токен в набор токенов, у каждого
из которых свой список инструментов и свои границы аргументов:

```json
{
  "version": 1,
  "tokens": [
    {
      "file": "/etc/mcp-node/tokens/build",
      "tools": ["sys_info", "exec", "read_file", "list_dir"],
      "exec_argv0": ["/usr/bin/git", "/usr/bin/make"],
      "exec_cwd": ["/srv/build"],
      "max_timeout_s": 120,
      "read_paths": ["/srv/build"],
      "read_deny": ["/srv/build/keys"]
    },
    {"file": "/etc/mcp-node/tokens/admin", "allow_all": true}
  ]
}
```

Нода проверяет каждый вызов до запуска: запрещённый `exec` не стартует,
запрещённая запись не открывает файл. Политика ограничивает argv[0], `cwd`,
пути чтения и записи, потолок таймаута и режим создаваемых файлов. Пути
нода канонизирует (symlink, `..`) и сравнивает по целым сегментам. Сессии
принадлежат токену, который их открыл. Отказ приходит как
`{"ok": false, "error": "PolicyDenied", "reason": ...}` и попадает в аудит-лог
событием `policy.deny`. Значения токенов в политику и лог не попадают.

Без переменной нода ведёт себя как раньше. При заданной политике собственный
токен ноды (`MCP_NODE_TOKEN_FILE`) обязан сам быть одним из `tokens[].file` —
иначе нода не стартует с `InvalidConfig`. Парсер строгий: неизвестный ключ
или противоречие останавливают старт. Хаб с политикой не стартует, потому
что маршрут `/n/<name>/mcp` пересылает тела нодам как есть; политику
ставят на каждую ноду. Разрешённый интерпретатор (`python3`, `bash`) по-прежнему
означает произвольный код. Подробности и ограничения: [docs/arg-gating.md](docs/arg-gating.md).

## Конфигурация

Переменные окружения плюс два флага командной строки: `--connect` (цель
обратного подключения) и `--state-dir` (журнал durable-сессий; то же, что
`MCP_NODE_STATE_DIR`, флаг главнее).

| Переменная | По умолчанию |
| --- | --- |
| `MCP_NODE_STATE_DIR` | не задано; когда задано (или передан `--state-dir`), `exec_start` принимает `durable:true`, и сессии переживают рестарт ноды. Каталог обязан быть приватным (`0700`), принадлежать ноде и блокируется на всё время жизни ноды |
| `MCP_NODE_STATE_MAX_BYTES` | `67108864` (64 МиБ); суммарный бюджет допуска durable-сессий (резерв на сессию: 2 x лимит вывода + 80 КиБ; нода проверяет размеры спулов при каждом обновлении и на свипе с частотой 1 Гц, а сессия, чьи суммарные логи переросли резерв, убивается с проверенной идентичностью и отвечает `completion_reason: "output_cap"` — граница best-effort: писатель может перелететь её между проверками, а вывод, записанный пока нода лежала, сверяется, а не предотвращается, при следующем старте) |
| `MCP_NODE_HOST` | `127.0.0.1` (IP-литерал) |
| `MCP_NODE_PORT` | `8341` |
| `MCP_NODE_TOKEN_FILE` | `./token` |
| `MCP_NODE_POLICY_FILE` | не задано (без прав по аргументам; см. [docs/arg-gating.md](docs/arg-gating.md)) |
| `MCP_NODE_ALLOWED_HOSTS` | `127.0.0.1:*,localhost:*,[::1]:*` |
| `MCP_NODE_ALLOWED_ORIGINS` | `http://127.0.0.1:*,http://localhost:*,http://[::1]:*` |
| `MCP_NODE_NAME` | `mcp-node` (имя в serverInfo) |
| `MCP_NODE_MAX_OUT` | `400000` байт на поток вывода, дальше `truncated_*` + `lost_*_bytes` |
| `MCP_NODE_MAX_CONN` | `128` одновременных соединений, дальше 503 |
| `MCP_NODE_MAX_SESSIONS` | `64` живых сессий |
| `MCP_NODE_SESSION_TTL_S` | `600`, задержка сбора завершённых сессий |
| `MCP_NODE_SOCKET_TIMEOUT_S` | `60` |
| `MCP_NODE_MAX_INFLIGHT_BYTES` | `67108864`, суммарный объём тел запросов в полёте |
| `MCP_NODE_TEXT_MIRROR` | `1`; `0` возвращает только `structuredContent`, вдвое сокращая ответ |
| `MCP_NODE_INSECURE` | не задано; `1` разрешает пустой токен (избегайте) |
| `MCP_NODE_STDIO` | не задано; `1` — обслуживать одного клиента через stdin/stdout, без слушателя (то же, что `--stdio`) |
| `MCP_NODE_AUDIT_FILE` | не задано; включает [аудит-лог](docs/audit-log.md) по этому пути |
| `MCP_NODE_AUDIT_KEY_FILE` | не задано; HMAC-ключ цепочки аудита (0600), отдельный от токена и секрета связи |
| `MCP_NODE_AUDIT_ARGS` | `summary`; `full` пишет argv и пути целиком, содержимое — никогда |
| `MCP_NODE_AUDIT_ON_FULL` | `block`; `drop` сбрасывает записи при зависшем диске с цепочечным маркером `dropped` |
| `MCP_NODE_AUDIT_MAX_BYTES` | `67108864`; сверх этого файл ротируется в `<file>.<chain-gen>.<first-seq>` (никогда не заменяя существующий файл), и цепочка продолжается |

`mcp-node --version` печатает версию, `--help` — флаги; любой другой
аргумент, кроме них, `--connect`, `--stdio` и `--state-dir`, — ошибка.
Единственная подкоманда — `mcp-node audit-verify [--anchor] <file>...`,
которая проверяет цепочку аудит-лога офлайн.

Переменные обратного подключения (`MCP_NODE_CONNECT*`, `MCP_NODE_HUB_*`)
перечислены в [docs/reverse-connect.md](docs/reverse-connect.md).

## Диагностика

| Симптом | Что делать |
| --- | --- |
| 401 | Неверный или отсутствующий токен. Если шлёте оба заголовка, они должны совпадать. |
| 421 | Добавьте `host:port`, через который подключаетесь, в `MCP_NODE_ALLOWED_HOSTS`. |
| 403 | `Origin` браузера не входит в `MCP_NODE_ALLOWED_ORIGINS`. |
| 415 | Отправьте `Content-Type: application/json`. |
| Connection refused | Проверьте `MCP_NODE_HOST`/`MCP_NODE_PORT`; loopback недоступен с других машин. |
| Выход при старте | Создайте непустой файл токена. |

## Дорожная карта

Уже в коде: обратное подключение со взаимным HMAC-рукопожатием плюс аутентифицированные кадры с проверкой порядка, TLS на канале ноды (на всех платформах), лимиты рукопожатий по источнику, аудит-лог с защитой от подделки, права токенов по инструментам и аргументам, exec-сессии, которые переживают обрыв линка или рестарт хаба, durable exec-сессии, которые переживают рестарт ноды (opt-in, Linux), cosign-подписанные релизы с provenance сборки.

Дальше: пары ключей на каждую ноду вместо общих секретов, durable-сессии на macOS/Windows и PTY для интерактивных TUI. API пока `0.x` и может ещё меняться до 1.0.

## Сборка из исходников

Нужен Zig 0.16.

```sh
git clone https://github.com/alexchen-sys/mcp-node-zig
cd mcp-node-zig
zig build test
zig build -Doptimize=ReleaseSafe   # → zig-out/bin/mcp-node
```

На Linux бинарь статический, без libc. macOS линкует только libSystem; Windows — только kernel32/ntdll.
